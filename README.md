核心项目
智能素材审核 Agent 系统	企业内部业务系统
Google ADK　|　DeepSeek　|　Python　|　Function Calling　|　MCP
6 个子 Agent、30+ 工具、4 类查询数据源（CK / ODPS / MySQL / ES）、4.0 / 5.0 双版本口径。核心矛盾：模型输出不确定，而审核流程不允许出错。
- ① 工具契约（模型会传错参数）：以 registry 为唯一事实源，导入期校验注册表、白名单与实现三方一致；调用前校验 6 类参数并返回可自纠错误，避免参数异常中断整轮对话。将参数静默通过、查询范围放大的风险由线上事故前移为调用前拒绝。
- ② 长任务（单请求 900 秒，ODPS 查询需数十分钟）：改为提交即返回，进度写入文件作为 checkpoint，按实例 ID 续跑；多日查询拆分为子任务，部分失败时保留成功结果。刷新或服务重启后可补齐，长查询不因页面关闭丢失。
- ③ 大结果（50 万行曾致服务内存达 5.8GB 并 OOM）：改为逐行流式落盘，并按读者拆分结果：模型侧仅接收行数、列名与下载链接，前端侧渲染表格。内存占用由 GB 级降至单行加分片缓冲，同时避免模型转述行内容。
- ④ 多 Agent（取舍：不做跨 Agent 转交）：root 仅做一级路由，5 个子 Agent 不互相转交、各自持有完整工具集，换取状态传递可控；权衡是子 Agent 工具数量增加、提示词变长。
- ⑤ 评测数据集：3 套数据集共 58 条用例（24 / 19 / 15），覆盖 22/33 个工具路径；用例取自 30 天线上日志的 226 条去重提问，依据真实问法设计。
- ⑥ 判定口径：接入 ADK 官方 TrajectoryEvaluator，先做 args 成对归一化（仅比对 key 集合），解决期望仅含工具名、实际参数含日期与广告主 ID 导致全部判 0 的问题；再按三种顺序语义匹配打分。评测器不可用时记为未判定，不计入通过率。
- ⑦ 评测边界：5 个写操作工具不纳入自动化评测：影响线上真实数据且无法重复执行，改由审批链路与操作日志覆盖。该边界为有意设定。
项目：从代码规则到可检索知识库（RAG）
规则库知识化：静态解析 → 词角色 → 分块编译	内部系统
Python　|　AST 静态解析　|　向量知识库　|　ADK
- 静态提取与词角色：规则分散于代码字面量、配置文件与线上缓存三处；采用 ast.parse 静态提取，不 import、不执行（规则模块导入时会连接缓存、加载词表并构建自动机）。解析布尔 match 表达式，将词分为触发 / 扣除 / 否决 / 开关四类（反例词不计入占用），无法识别的写法标记待复核。
- 分块与校验：代表词之外的词按字符预算拆分续块，块首写入短标记作为切片边界；约 1 万触发词编译为 700 余个切片。编译后以守恒断言校验词无丢失，将词条缺失转为构建失败。
评测体系与效果
- 用例来源：30 天线上日志 1,639 条，经 748 条有效请求去重得 226 条提问；分类文本、曝光明细、屏蔽落地页三类零命中能力单独补充人工用例，不纳入抽样。
- 用例缺陷：3 条用例引用重构后已删除的工具名，持续失败使通过率系统性偏低约 5pp 并干扰归因。现改为加载期校验，工具名不存在即报错；并对注册表、白名单与实现加三方一致性断言。

traceeval：tool-calling agent 的轨迹级评测器	开源项目
- 评测口径：面向工具调用轨迹而非最终答复：覆盖调用未返回（假成功）、未判定与失败三态、参数漂移归一化、重复与过度调用；支持 LangChain、LangGraph、ADK、OTel 四种接入。

- 框架对比：同模型、同工具、同任务下，LangGraph、LangChain、ADK 三者轨迹一致（各 48/48）；选型依据生态成熟度与接入成本，新框架接入须通过兼容测试。
